Source Leak

Memahami bagaimana repository atau source code yang terekspos dapat memberikan konteks tentang aplikasi: struktur kode, riwayat perubahan, konfigurasi, dependency, endpoint, dan kemungkinan kelemahan lain. Satu exposure bukan otomatis akses ke server, tetapi dapat menjadi sumber informasi untuk investigasi lanjutan.

01 / Fundamentals

Apa Itu Source Leak?

Source Leak dalam dokumentasi ini berarti source code, repository metadata, version history, atau file pengembangan yang seharusnya tidak dapat diakses publik ternyata terekspos melalui web server, storage, backup, atau mekanisme distribusi aplikasi.

Exposure dapat berupa file source code individual, arsip backup, direktori repository seperti .git, .svn, atau .hg, maupun artefak build dan konfigurasi. Tingkat informasi yang terbuka berbeda-beda: sebagian hanya memperlihatkan nama file, sementara kondisi lain dapat memungkinkan pengambilan banyak bagian repository.

Inti konsep ZeroHitman: Source Leak bukan hanya “mendapatkan source code”. Temuan ini dapat menjadi titik awal untuk memahami bagaimana aplikasi dibangun, data mengalir, fitur bekerja, komponen apa yang dipakai, dan area mana yang layak ditinjau lebih lanjut.
Batas interpretasi: repository exposure tidak otomatis berarti server telah dikuasai, credential yang terlihat masih aktif, atau setiap kandidat bug dapat dieksploitasi. Setiap temuan perlu diverifikasi sesuai scope, bukti, dan kondisi aktual.
02 / Version Control

Git, SVN, dan Mercurial

Version Control System (VCS) menyimpan perubahan source code dari waktu ke waktu. VCS membantu developer bekerja bersama, membandingkan perubahan, membuat branch, dan memulihkan versi sebelumnya. Metadata dan history yang bermanfaat bagi developer dapat menjadi sensitif jika ikut dipublikasikan tanpa sengaja.

VCSMetadata umumHal yang perlu dipahami
Git.git/Object database, references, index, dan reflogs. File repository bukan sekadar folder source biasa.
Subversion (SVN).svn/Working-copy metadata dan informasi administrasi lokal; struktur dan perilakunya berbeda dari Git.
Mercurial (Hg).hg/Repository metadata dan revlog yang menyimpan revision history.

Jangan menganggap ketiganya memiliki struktur, format, atau cara pemulihan data yang sama. Penilaian harus mengikuti VCS yang benar-benar digunakan dan versi/konfigurasi yang ditemukan.

Dalam Git, model data inti mencakup objects (commit, tree, blob, tag), references, index, dan reflogs. Karena itu, exposure direktori .git berpotensi mengungkap lebih dari file yang sedang terlihat pada halaman website.

03 / Root Causes

Mengapa Repository Bisa Terekspos?

DevelopmentRepository berada di direktori kerja developer atau build.
DeploymentArtefak development ikut tersalin ke web root atau image produksi.
Public AccessKonfigurasi server tidak memblokir akses ke metadata atau file internal.

Beberapa penyebab yang umum:

  • Document root terlalu luas: direktori yang disajikan web server mencakup repository atau file pengembangan.
  • Deployment tidak bersih: folder VCS, backup, arsip, file sementara, atau konfigurasi ikut terunggah.
  • Aturan deny tidak lengkap: server hanya memblokir pola tertentu, atau aturan tidak berlaku pada lokasi/alias yang digunakan.
  • Static file serving terlalu permisif: file tersembunyi atau file tanpa ekstensi yang dianggap berbahaya tetap dapat dilayani.
  • Salinan atau backup: arsip source, dump, atau salinan lama tertinggal di lokasi publik.
Menghapus link dari halaman website tidak sama dengan membatasi akses. Kontrol harus diterapkan pada web server, storage, deployment pipeline, dan permission repository.
04 / Information Mapping

Informasi Apa yang Bisa Diperoleh?

Nilai Source Leak ditentukan oleh isi yang benar-benar tersedia. Tidak semua repository berisi secret atau kelemahan. Mulailah dengan mengklasifikasikan informasi, bukan langsung mengasumsikan dampaknya.

KategoriContoh informasiNilai investigasi
Application structureFolder, module, controller, model, service, templateMemahami arsitektur dan batas komponen.
ConfigurationEnvironment variable names, host, port, path, feature flagsMemahami konfigurasi dan dependensi runtime. Nilai rahasia harus diperlakukan sensitif.
Credentials & secretsDatabase password, API token, signing key, cloud credentialPotensi akses ke sistem lain jika masih valid dan memiliki permission.
Version historyFile yang dihapus, perubahan konfigurasi, commit messageMemahami perubahan lama dan konteks bug yang pernah diperbaiki.
DependenciesPackage name, version constraints, lock filesMenentukan komponen dan versi untuk pemeriksaan advisories.
Application routesRoute definitions, API paths, middlewareMemetakan attack surface dan kontrol akses yang perlu ditinjau.
Infrastructure cluesDockerfile, compose files, CI configuration, web server configMemahami service topology dan proses deployment.
05 / Code Understanding

Source Code Analysis

Setelah source tersedia secara sah dalam scope assessment, langkah penting adalah memahami alur data dan batas kepercayaan. Pencarian kata kunci dapat membantu menemukan lokasi yang menarik, tetapi hasil pencarian bukan bukti vulnerability.

1. Secret dan credential references

Periksa apakah kode atau konfigurasi memuat credential, token, key, certificate, atau endpoint internal. Bedakan secret value yang benar-benar tertanam dari nama environment variable atau placeholder. Jangan menyalin nilai rahasia ke report publik; catat lokasi, jenis, status validasi yang diizinkan, dan dampak potensial.

2. File inclusion dan file handling

Telusuri bagaimana aplikasi membentuk path, memilih file, memproses upload, mengunduh file, atau menyajikan dokumen. Fokus pada alur input → validasi → operasi file → output, termasuk kontrol path dan authorization.

3. Database query

Tinjau query yang dibangun secara dinamis, penggunaan raw query, parameter binding, stored procedure, serta aliran data dari request atau data tersimpan. Temuan source review dapat menjadi kandidat pemeriksaan SQL Injection, tetapi harus dibuktikan pada konteks kode dan konfigurasi yang relevan.

4. Dangerous sinks dan tainted input

Fungsi seperti eval, system, process execution, deserialization, template rendering, atau pemanggilan HTTP perlu dinilai berdasarkan asal input, sanitasi, allow-list, dan kontrol yang mengelilinginya. Keberadaan fungsi saja tidak cukup untuk menyatakan vulnerability.

5. Authentication, authorization, dan routes

Periksa middleware, policy, role checks, ownership checks, route groups, serta perbedaan antara autentikasi dan otorisasi. Route tersembunyi bukan otomatis route yang dapat diakses tanpa izin.

Metode berpikir: jangan berhenti pada “menemukan kata system”. Cari tahu siapa yang mengontrol nilai, bagaimana nilai mengalir, kontrol apa yang diterapkan, dan apakah jalur tersebut dapat dicapai dalam kondisi nyata.
06 / Historical Context

Version History Analysis

Repository history dapat mempertahankan informasi yang sudah tidak terlihat pada versi aplikasi saat ini. File yang dihapus dari working tree belum tentu hilang dari history. Hal ini dapat membantu memahami evolusi aplikasi, tetapi juga membuat secret lama tetap sensitif.

Commit changesApa yang ditambahkan atau diubah?
Deleted filesApakah file lama mengandung konfigurasi atau kode penting?
Branch & tagsApakah ada versi pengembangan atau release berbeda?

Reflog dan metadata

Reflogs mencatat perubahan references dalam repository lokal. Metadata commit dapat menunjukkan author, waktu, dan pesan commit. Email atau username developer adalah metadata identitas, bukan credential autentikasi.

Perhatikan perbedaan antara file yang pernah ada, file yang masih dapat dijangkau oleh references, dan data yang benar-benar dapat diambil dari exposure yang diamati. Jangan menyimpulkan seluruh history dapat diakses hanya karena satu endpoint metadata merespons.

Catatan respons insiden: jika secret ditemukan dalam history, menghapus file pada commit terbaru tidak cukup. Pemilik sistem perlu mencabut atau merotasi secret terlebih dahulu, lalu menilai kebutuhan pembersihan history, forks, clones, cache, dan salinan lain.
07 / Configuration Review

Configuration Analysis

File konfigurasi dapat mengungkap bagaimana aplikasi dijalankan dan layanan apa yang digunakannya. Namun, file yang hanya menunjukkan nama variable atau hostname belum tentu mengandung credential aktif.

ArtefakInformasi yang mungkin adaHal yang perlu diverifikasi
.env / sample envDB connection, mail, cache, APP_KEY, service endpointsApakah file memuat nilai nyata atau placeholder? Apakah secret masih aktif?
composer.jsonPHP packages dan version constraintsBandingkan dengan lock file dan versi runtime yang digunakan.
package.jsonNode packages dan scriptsPastikan dependency yang digunakan pada deployment sesuai.
requirements.txtPython packagesPeriksa versi terpasang, transitive dependencies, dan advisory yang relevan.
Dockerfile / ComposeBase image, service names, port mapping, build argumentsFile mungkin berbeda dari konfigurasi produksi aktual.
.htaccess / web server configRewrite rules, document root clues, access restrictionsPastikan file tersebut benar-benar digunakan oleh server.
CI/CD configurationBuild steps, deployment jobs, variable names, artifact pathsJangan menganggap nama variable sebagai nilai secret atau akses pipeline.

Contoh penting: APP_KEY, JWT signing key, cloud key, dan database password memiliki fungsi serta dampak berbeda. Kebocoran salah satunya tidak boleh digeneralisasi menjadi “admin access” atau “RCE”. Dampak bergantung pada penggunaan, scope, validitas, dan kontrol yang diterapkan.

08 / Software Composition

Dependency Analysis

Dependency file memberi petunjuk mengenai library, framework, dan versi yang diminta aplikasi. Ini dapat membantu peneliti menentukan advisories atau CVE yang layak diperiksa.

  • Manifest: menjelaskan dependency yang dideklarasikan dan batas versi.
  • Lock file: biasanya memberi detail versi resolusi yang lebih spesifik, tetapi tetap perlu dibandingkan dengan artefak deployment.
  • Transitive dependency: komponen dapat ditarik oleh dependency lain dan tidak selalu tercantum sebagai kebutuhan langsung.
  • Runtime mismatch: repository yang terekspos belum tentu sama dengan kode yang sedang berjalan di production.
CVE lookup adalah langkah verifikasi, bukan kesimpulan. Cocokkan nama package, versi yang benar-benar digunakan, konfigurasi, komponen yang terjangkau, dan kondisi kerentanan. Jangan menyatakan aplikasi rentan hanya karena menemukan nama library yang pernah memiliki CVE.
09 / Attack Surface

New Attack Surface Discovery

Source code dan konfigurasi dapat membantu menyusun peta permukaan aplikasi. Tujuannya bukan menganggap setiap path sebagai celah, melainkan mengetahui komponen mana yang perlu diperiksa dalam scope.

Routes & endpoints

Daftar route, API path, HTTP method, middleware, dan controller yang terhubung.

Parameters

Parameter request, filter, identifier, upload field, dan nilai yang memengaruhi operasi.

Feature flags

Debug mode, beta feature, test mode, atau konfigurasi yang mengubah perilaku aplikasi.

Internal services

Database, cache, queue, object storage, internal API, dan service dependencies.

Nama endpoint atau parameter yang ditemukan dari source perlu dibandingkan dengan route yang benar-benar aktif. Kode lama, route yang tidak diregistrasi, feature flag nonaktif, atau deployment yang berbeda dapat membuat informasi repository tidak mencerminkan attack surface production.

10 / Candidate Validation

Menilai Kandidat Vulnerability dari Source

Source review sering menghasilkan leads atau kandidat temuan. Agar tidak menghasilkan false positive, gunakan alur penilaian yang konsisten:

  1. Identify: catat file, fungsi, route, dependency, dan konteks temuan.
  2. Trace: telusuri asal input sampai ke operasi sensitif (source-to-sink).
  3. Review controls: periksa validation, parameterization, authorization, allow-list, sandbox, dan error handling.
  4. Check reachability: tentukan apakah jalur kode aktif dan dapat dicapai dalam kondisi target.
  5. Validate safely: lakukan verifikasi hanya pada aset dan metode yang secara eksplisit diizinkan.
  6. Document: pisahkan fakta, indikasi, asumsi, dan dampak yang telah dibuktikan.
Hasil grep, nama fungsi berbahaya, dependency lama, atau route tersembunyi adalah petunjuk awal. Masing-masing memerlukan analisis konteks sebelum disebut vulnerability.
11 / ZeroHitman Tree V5.0

Percabangan Source Leak

Bagian ini mempertahankan enam kelompok utama dari Tree V5.0: Analisa Source Code, Git History, Config Analysis, Deserialization/Crypto, New Attack Surface, dan Backdoor/Supply Chain. Nama cabang dipertahankan agar pembaca dapat mencocokkan halaman ini dengan peta utama. Penjelasan di bawah memperjelas kondisi dan batas tiap cabang.

1. Analisa Source Code

  • DB creds: dapat menunjukkan konfigurasi akses database; validitas, privilege, network reachability, dan environment harus dinilai.
  • SMTP creds: dapat memberi akses ke layanan email jika aktif dan diizinkan; bukan bukti otomatis bahwa phishing dapat atau boleh dilakukan.
  • JWT secret: dapat memengaruhi kepercayaan token jika aplikasi benar-benar menggunakannya untuk signing dan tidak ada kontrol tambahan yang mencegah penyalahgunaan.
  • API / cloud / payment key: dampak bergantung pada scope permission, environment, expiry, dan batas layanan.
  • include/require: arahkan review ke validasi path dan file inclusion; bukan bukti LFI dengan sendirinya.
  • SQL query: arahkan review ke query construction, binding, dan data flow; bukan bukti SQLi otomatis.
  • Upload handler: tinjau type validation, storage location, filename handling, authorization, dan execution policy.
  • eval/system, unserialize, curl_exec: lakukan taint analysis dan review kontrol; keberadaan fungsi tidak cukup untuk menyimpulkan RCE, deserialization flaw, atau SSRF.
  • Route dan debug/test mode: petakan endpoint dan kondisi aktifnya, lalu verifikasi middleware serta konfigurasi runtime.

2. Git History

  • Perubahan lama dan deleted files: dapat memperlihatkan kode atau konfigurasi yang tidak lagi ada pada versi terbaru.
  • Reflog / metadata: dapat memberi konteks perubahan references dan identitas commit. Author email atau username bukan password.
  • .git/config dan remote URL: dapat mengungkap host repository atau struktur internal. Credential tertanam mungkin ada pada kasus tertentu, tetapi tidak boleh diasumsikan.
  • Branch dan tag lain: dapat menunjukkan versi atau fitur berbeda. Keberadaan branch tidak otomatis berarti branch tersebut digunakan di production.

3. Config Analysis

  • .env: periksa jenis konfigurasi dan apakah ada nilai rahasia nyata; APP_KEY tidak otomatis berarti cookie dapat dipalsukan atau akses admin didapat.
  • Redis credentials: dapat menunjukkan kredensial cache/service. RCE bukan dampak otomatis; bergantung pada versi, konfigurasi, hak akses, jaringan, dan jalur yang tersedia.
  • Composer, npm, dan Python manifests: menjadi dasar inventory dependency dan CVE lookup, lalu cocokkan dengan versi runtime.
  • Dockerfile dan web server config: memberi petunjuk arsitektur, port, path, dan routing; belum tentu identik dengan production.

4. Deserialization / Crypto

  • unserialize() dan PHAR-related behavior: periksa apakah data tidak tepercaya dapat mencapai proses deserialization, kelas yang tersedia, dan kondisi runtime. RCE tidak otomatis.
  • Weak crypto: algoritma atau konfigurasi lama dapat menurunkan keamanan, tetapi dampak tergantung tujuan penggunaan dan data yang dilindungi.
  • Hardcoded IV/salt: nilai statis dapat melemahkan desain tertentu; IV, salt, encryption key, dan password hash salt bukan hal yang sama.
  • Custom JWT: review algoritma, key management, claim validation, expiry, issuer/audience, dan authorization. Custom implementation bukan otomatis authentication bypass.

5. New Attack Surface

  • Hidden endpoint dan admin endpoint: dapat memperluas peta route; tetap periksa autentikasi, authorization, dan apakah route aktif.
  • Hidden parameter dan beta feature: dapat menunjukkan fungsi yang tidak terlihat pada UI; jangan menganggap parameter dapat mengaktifkan debug tanpa bukti.
  • Internal API: pahami trust boundary dan akses yang dirancang. Pengujian harus tetap dalam scope dan tidak melewati batas izin.

6. Backdoor / Supply Chain

  • Backdoor in source: kode mencurigakan atau akses tersembunyi perlu ditinjau melalui konteks, provenance, dan perubahan yang tidak sah; jangan menyimpulkan backdoor hanya dari nama fungsi.
  • Malicious build: periksa integritas build pipeline, artifact provenance, runner, dan proses deployment.
  • Malicious dependency: tinjau sumber package, maintainer, perubahan versi, integrity metadata, dan perilaku yang tidak diharapkan.
  • Hardcoded admin: periksa apakah akun/credential benar-benar aktif, bagaimana autentikasi dan authorization diterapkan, serta apakah konfigurasi hanya untuk test.
Catatan: enam kelompok ini adalah kategori investigasi dari Tree V5.0, bukan daftar hasil yang pasti muncul pada setiap Source Leak.
12 / Cross-Technique

Hubungan Source Leak dengan Teknik Lain

Nilai terbesar Source Leak dalam pola pikir ZeroHitman adalah kemampuannya membuka konteks untuk cabang lain. Hubungan tersebut bersifat kondisional: informasi dari source dapat membantu menemukan kandidat vulnerability, tetapi bukan berarti vulnerability tersebut otomatis ada.

Informasi dari Source LeakCabang investigasi yang mungkin relevanKondisi yang harus diperiksa
Query dinamis dan aliran inputSQL InjectionInput tidak tepercaya memengaruhi struktur query tanpa binding yang aman.
File inclusion dan path handlingLFI / Path TraversalKontrol path lemah dan jalur kode dapat dicapai.
Upload handlerUnrestricted File Upload / file handling flawValidasi, penyimpanan, akses, dan eksekusi file bermasalah.
HTTP client atau URL fetcherSSRFInput mengontrol tujuan request dan kontrol egress/allow-list tidak memadai.
Debug configuration dan exception handlingInformation Disclosure / debug exposureInformasi sensitif benar-benar terekspos pada runtime.
Dependency dan versi frameworkCVE researchVersi terpasang, konfigurasi, reachability, dan prasyarat advisory cocok.
Credential atau signing keyCredential exposure / authentication reviewSecret valid, scope memadai, dan penggunaan aktual dapat dibuktikan secara aman.
Build pipeline dan dependency sourceSupply-chain securityAda bukti integritas atau provenance yang gagal, bukan hanya file build yang tersedia.

Contoh pola pikir: menemukan file repository adalah temuan awal. Source code dapat memperlihatkan query builder yang perlu ditinjau; lock file dapat mengarahkan pemeriksaan dependency; konfigurasi dapat menunjukkan service yang digunakan. Masing-masing cabang dipilih berdasarkan bukti baru, bukan karena semua cabang harus dikejar.

13 / Risk Assessment

Dampak dan Prioritas

Dampak Source Leak tidak ditentukan hanya oleh nama direktori yang terekspos. Penilaian harus melihat kerahasiaan informasi, kemampuan pihak luar mengaksesnya, sensitivitas data, apakah secret masih berlaku, dan sistem lain yang bergantung padanya.

  • Confidentiality: source code, desain internal, data konfigurasi, atau secret dapat terbaca.
  • Integrity: dapat meningkat jika informasi yang terekspos juga membuka jalur akses yang sahnya terbatas dan kontrol lain gagal. Exposure sendiri tidak membuktikan kemampuan mengubah sistem.
  • Availability: biasanya bukan dampak langsung repository exposure; perlu bukti jalur yang dapat mengganggu layanan.
  • Business impact: secret pihak ketiga, payment integration, cloud permission, atau informasi pelanggan dapat memiliki konsekuensi berbeda.

Prioritaskan informasi berdasarkan sensitivitas, validitas, privilege, jangkauan akses, dan bukti penggunaan. Redact secret pada laporan dan simpan bukti sensitif dengan akses terbatas.

14 / Defense & Incident Response

Mitigasi dan Respons

Pencegahan

  • Jangan tempatkan repository metadata, backup, secret, atau artefak development di public web root.
  • Gunakan deployment artifact yang bersih dan allow-list file yang memang harus dipublikasikan.
  • Blokir akses ke metadata VCS dan file konfigurasi pada web server, tetapi jangan menjadikan rule tersebut satu-satunya kontrol.
  • Simpan secret di secret manager atau mekanisme konfigurasi yang sesuai; hindari hardcoding.
  • Terapkan least privilege, short-lived credentials bila memungkinkan, dan pemisahan environment.
  • Gunakan secret scanning pada commit/push dan pipeline CI/CD, serta review perubahan sebelum release.
  • Inventarisasi dependency dan pantau advisories dengan mencocokkan versi yang benar-benar digunakan.

Jika exposure ditemukan

  1. Batasi akses publik dan simpan bukti minimum yang diperlukan untuk investigasi.
  2. Identifikasi jenis data dan secret yang mungkin terpapar tanpa menyebarkan nilai rahasia.
  3. Cabut atau rotasi credential yang berpotensi terekspos; jangan menunggu pembersihan history selesai.
  4. Tinjau log akses, penggunaan credential, repository clones/forks, cache, dan artifact lain sesuai kemampuan organisasi.
  5. Jika perlu membersihkan history, rencanakan koordinasi karena rewrite dapat mengubah commit hash dan berdampak pada clone, branch, tag, serta workflow kolaborator.
  6. Perbaiki deployment pipeline dan tambahkan kontrol pencegahan agar exposure tidak terulang.
Jangan menganggap menghapus file dari commit terbaru sudah menyelesaikan kebocoran. Secret dapat tetap ada di history, clone, fork, cache, atau salinan lain. Untuk credential, langkah pertama yang paling penting adalah revoke/rotate.
15 / ZeroHitman Mindset

Kesimpulan

Source Leak adalah pintu informasi. Nilai utamanya bukan sekadar memperoleh source code, melainkan menggunakan informasi yang tersedia untuk memahami aplikasi dan menentukan cabang investigasi berikutnya.

Mulai dari memahami struktur repository, kemudian klasifikasikan source code, history, konfigurasi, dependency, dan attack surface. Pisahkan fakta dari asumsi. Sebuah credential mungkin sudah tidak aktif; sebuah dependency mungkin tidak digunakan di production; sebuah fungsi sensitif mungkin dilindungi validasi dan authorization.

Prinsip ZeroHitman: satu temuan dapat membuka banyak pertanyaan. Kumpulkan informasi yang relevan, nilai kualitasnya, lalu ikuti bukti. Tidak semua cabang harus ditempuh dan tidak semua petunjuk adalah vulnerability.
