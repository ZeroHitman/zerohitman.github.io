01 / Fundamentals

Apa Itu Local File Inclusion?

Local File Inclusion (LFI) adalah kelemahan pada aplikasi ketika aplikasi memuat atau memasukkan file lokal berdasarkan nilai yang dapat dipengaruhi pengguna, tanpa pembatasan path dan validasi yang memadai.

Istilah inclusion biasanya digunakan ketika aplikasi menggunakan mekanisme bahasa atau framework untuk memasukkan file ke dalam proses aplikasi. Pada PHP, contohnya adalah penggunaan konstruksi seperti include dan require. Jika pemilihan file dikendalikan input yang tidak aman, penyerang mungkin dapat membuat aplikasi mengakses file di luar file yang semestinya dipilih.

Konsekuensi LFI bergantung pada bagaimana file diproses. File yang hanya dibaca sebagai data tidak selalu memiliki dampak yang sama dengan file yang diinterpretasikan sebagai kode. Karena itu, LFI perlu dibedakan dari pembacaan file biasa, path traversal, dan eksekusi kode.

Inti konsep: masalah utamanya bukan sekadar karakter ../ atau nama file. Masalahnya adalah keputusan aplikasi tentang file apa yang boleh dimuat, dari lokasi mana, dan dengan cara apa file tersebut diproses.
02 / Application Flow

Bagaimana File Inclusion Bekerja?

Secara konseptual, aplikasi dapat menyediakan fitur untuk memilih template, halaman bahasa, modul, atau konten berdasarkan parameter. Aplikasi kemudian menerjemahkan pilihan tersebut menjadi lokasi file yang akan digunakan.

  • Input diterima. Aplikasi menerima nilai dari parameter URL, form, cookie, header, atau sumber lain.
  • Nilai dipakai untuk memilih file. Kode aplikasi menggabungkan atau meneruskan nilai tersebut ke mekanisme file handling.
  • Validasi dan pembatasan dilakukan. Aplikasi seharusnya memastikan pilihan berasal dari daftar yang diizinkan dan tetap berada dalam direktori yang dimaksud.
  • File diproses. Jika kontrol tidak memadai, aplikasi dapat memuat file yang tidak dimaksudkan untuk diakses melalui fitur tersebut.
  • Dampak dinilai. Peneliti memeriksa jenis file, isi yang terekspos, cara file diproses, serta hak akses proses aplikasi.

    • Contoh konseptual yang aman

    // Pola berisiko: pilihan file berasal langsung dari input pengguna
$page = $_GET['page'] ?? 'home';
include($page . '.php');

// Pola yang lebih aman: input dipetakan ke daftar pilihan tetap
$pages = [
  'home' => __DIR__ . '/pages/home.php',
  'about' => __DIR__ . '/pages/about.php'
];
$key = $_GET['page'] ?? 'home';
if (!array_key_exists($key, $pages)) {
  http_response_code(404);
  exit;
}
include($pages[$key]);

    Contoh tersebut menunjukkan perbedaan desain: versi pertama membangun path dari input, sedangkan versi kedua hanya menerima identifier yang dipetakan ke file yang telah ditentukan. Contoh ini bersifat ilustratif dan bukan demonstrasi eksploitasi.

    03 / Root Causes

    Mengapa LFI Bisa Terjadi?

    Input langsung menjadi path

    Nilai dari request dipakai untuk menentukan file tanpa pemetaan pilihan yang ketat.

    Validasi hanya berbasis blacklist

    Aplikasi mencoba menolak beberapa pola, tetapi tidak membatasi file yang boleh dipilih secara positif.

    Path tidak dinormalisasi

    Aplikasi tidak memastikan hasil resolusi path tetap berada di direktori yang ditetapkan.

    Kontrol akses file terlalu luas

    Proses aplikasi dapat membaca file sensitif yang sebenarnya tidak diperlukan untuk menjalankan fungsi web.

    Perbedaan konfigurasi lingkungan

    Perilaku path, permission, wrapper, dan filesystem dapat berbeda antara development, staging, dan production.

    Desain plugin atau template dinamis

    Fitur extensibility yang fleksibel dapat menjadi berisiko jika sumber modul atau template tidak dibatasi.

    Validasi yang hanya menghapus substring tertentu bukan kontrol keamanan yang kuat. Pendekatan yang lebih baik adalah allowlist identifier, pemetaan ke lokasi tetap, canonicalization yang benar, dan pembatasan hak akses proses.
    04 / Terminology

    LFI, Path Traversal, dan Arbitrary File Read

    Ketiganya berkaitan dengan pemilihan atau akses file, tetapi bukan istilah yang dapat dipertukarkan begitu saja.

    IstilahMaknaHal yang perlu dibuktikan
    Path TraversalInput memengaruhi path sehingga proses dapat menunjuk lokasi di luar direktori yang dimaksud.Apakah aplikasi benar-benar mengakses path di luar batas yang ditetapkan?
    Arbitrary File ReadKemampuan membaca file yang tidak semestinya dapat dibaca oleh pemanggil.File apa yang dapat dibaca, oleh komponen mana, dan dengan izin siapa?
    Local File InclusionAplikasi memasukkan atau memuat file lokal berdasarkan pemilihan yang dapat dipengaruhi pengguna.Apakah file diproses sebagai inclusion, dan apa perilaku interpreter terhadap file tersebut?
    Remote File Inclusion (RFI)Dalam konteks tertentu, aplikasi memuat sumber file dari lokasi remote.Apakah remote inclusion didukung dan diizinkan oleh runtime serta konfigurasi?
    Satu kelemahan dapat memiliki lebih dari satu karakteristik. Contohnya, bug pada parameter file dapat sekaligus memungkinkan path traversal dan file disclosure. Klasifikasi akhir harus mengikuti perilaku yang terbukti, bukan hanya nama parameter atau dugaan awal.
    05 / Classification

    Jenis dan Pola LFI

    Direct / Reflected LFI

    Aplikasi memuat file yang dipilih melalui input, dan hasil pemrosesannya dapat terlihat langsung pada respons. Visibilitas isi file bergantung pada format respons dan cara aplikasi menangani output.

    Indirect LFI

    Nilai yang memengaruhi pemilihan file dapat tersimpan lebih dahulu, misalnya pada preferensi pengguna, pilihan bahasa, atau konfigurasi. File baru diproses ketika fungsi lain dijalankan.

    Blind LFI

    Aplikasi mungkin mengakses file, tetapi isi file tidak dikembalikan secara langsung. Penilaian dilakukan melalui perbedaan perilaku yang dapat diamati, misalnya status respons, pesan kesalahan, atau perubahan waktu. Pengamatan harus dirancang hati-hati agar tidak salah mengartikan gangguan jaringan atau variasi performa sebagai bukti.

    Conditional / Context-dependent LFI

    Perilaku inclusion dapat bergantung pada autentikasi, role, konfigurasi runtime, ekstensi file, atau alur aplikasi tertentu. Karena itu, satu endpoint mungkin berperilaku berbeda untuk pengguna dan kondisi yang berbeda.

    06 / Impact

    Dampak dan Informasi yang Mungkin Terpapar

    LFI tidak memiliki satu dampak baku. Dampak ditentukan oleh file yang dapat dijangkau, permission proses, cara file diproses, serta informasi yang terdapat di dalamnya.

    Kategori informasiContoh konteksNilai investigasi
    System account metadataInformasi akun dan service pada sistem operasi.Memahami user yang ada dan konteks layanan; bukan bukti bahwa autentikasi jarak jauh dapat dilakukan.
    Application configurationKonfigurasi aplikasi, framework, atau web server.Memahami path, mode aplikasi, komponen, dan pengaturan keamanan.
    Environment variablesKonfigurasi runtime dan secret yang disuntikkan ke proses.Dapat mengungkap credential atau token; validitas dan scope-nya harus diverifikasi secara aman.
    Database configurationHost database, nama database, username, atau parameter koneksi.Membantu memetakan ketergantungan aplikasi; jangan menganggap credential masih aktif.
    Source codeFile PHP, template, route, atau konfigurasi framework.Membantu code review dan menemukan titik input, query, autentikasi, serta file handling lain.
    Logs and session dataLog aplikasi atau file session yang dapat dibaca proses.Dapat mengandung data sensitif; isi dan format bergantung pada implementasi.
    Container / orchestration metadataInformasi runtime container atau secret yang dipasang ke container.Membantu memahami batas isolasi; keberadaan file tidak berarti seluruh host dapat diakses.
    Credential exposure bukan akses otomatis. Secret yang terlihat dapat sudah kedaluwarsa, dibatasi scope, dinonaktifkan, atau hanya berlaku pada lingkungan tertentu. Validasi harus mengikuti izin dan prosedur client, tanpa mencoba menggunakan secret di luar scope.
    07 / Source Code Disclosure

    File Read Menuju Source Code Analysis

    Salah satu hasil investigasi yang bernilai dari file disclosure adalah pemahaman lebih baik terhadap source code. Pada aplikasi yang menggunakan PHP, file sumber dapat mengungkap alur pemrosesan request, pemanggilan database, autentikasi, file upload, dan pemilihan file.

    Informasi yang dapat dipetakan dari source code

    • Input handling: parameter, cookie, header, dan data yang disimpan sebelum digunakan.
    • Database interaction: query, model, serta pemisahan data dan perintah.
    • Authentication & authorization: middleware, role check, dan pemeriksaan kepemilikan objek.
    • File handling: upload, download, include, export, dan penghapusan file.
    • Application routes: endpoint yang tersedia dan fungsi yang dituju.
    • Dependencies: library dan versi yang perlu dibandingkan dengan advisory resmi.

    Source code disclosure sendiri belum tentu memberikan akses untuk mengubah aplikasi. Nilainya adalah membuka konteks untuk analisis lebih lanjut. Temuan baru seperti SQL Injection, Broken Access Control, atau kelemahan upload harus dibuktikan secara terpisah.

    Inilah contoh pola pikir ZeroHitman: temuan file read dapat menjadi titik awal source analysis; source analysis dapat mengarahkan peneliti ke kandidat vulnerability lain. Hubungan tersebut merupakan arah investigasi, bukan jaminan hasil.
    08 / PHP Runtime

    PHP Stream Wrappers

    PHP menyediakan stream wrappers, yaitu mekanisme yang memungkinkan fungsi file berinteraksi dengan berbagai jenis stream atau sumber data menggunakan skema tertentu. Wrapper bukan vulnerability dengan sendirinya. Dampaknya bergantung pada fungsi yang memakainya, konfigurasi PHP, dan validasi aplikasi.

    WrapperFungsi umumCatatan keamanan
    file://Mengakses filesystem lokal.Akses tetap dipengaruhi permission proses dan pembatasan lingkungan.
    php://Mengakses stream I/O PHP, termasuk input dan filter stream.Sub-scheme memiliki perilaku berbeda; tidak semuanya dapat digunakan sebagai target inclusion.
    data://Mewakili data yang ditanamkan pada URI.Penggunaan dibatasi konfigurasi seperti allow_url_fopen dan konteks fungsi; tidak otomatis berarti eksekusi kode.
    http:// / https://Mengakses resource melalui protokol HTTP(S) pada fungsi yang mendukungnya.Remote access berbeda dari local file inclusion dan dikendalikan konfigurasi runtime serta jaringan.
    ftp://Mengakses resource FTP pada fungsi yang mendukungnya.Perlu mempertimbangkan konfigurasi, kredensial, dan batas jaringan.
    zip://Mengakses anggota arsip ZIP melalui stream wrapper.Perilaku bergantung pada dukungan ekstensi dan cara aplikasi memproses file.
    phar://Mengakses konten arsip PHAR.Risiko deserialization historis bergantung pada operasi, versi PHP, dan gadget chain; sekadar menyebut wrapper bukan bukti RCE.
    expect://Wrapper dari ekstensi PECL Expect untuk interaksi proses.Tidak tersedia secara default pada banyak instalasi; keberadaan dan konfigurasi ekstensi harus diverifikasi.
    Penting: jangan menyamakan semua wrapper sebagai teknik LFI atau RCE. Beberapa wrapper hanya menyediakan akses stream; sebagian memerlukan ekstensi tambahan; dan perilakunya dapat berubah menurut versi serta konfigurasi PHP.
    09 / Runtime Artifacts

    Log dan Session sebagai Konteks Investigasi

    Log dan session merupakan file atau artefak runtime yang mungkin dapat dijangkau oleh proses aplikasi. Dalam kondisi tertentu, aplikasi yang rentan dapat memuat artefak tersebut. Namun, keberadaan file log atau session tidak otomatis menjadikannya jalur eksekusi.

    Log files

    Web server dan aplikasi dapat menyimpan request metadata, pesan error, atau aktivitas sistem. Format dan lokasi log ditentukan konfigurasi. Sebagian log mungkin memuat data yang dikendalikan pengguna, tetapi apakah data itu diperlakukan sebagai kode ketika file dimuat merupakan persoalan terpisah yang sangat bergantung pada interpreter, format, dan konteks.

    Session files

    Session dapat disimpan di filesystem, database, Redis, atau backend lain. Jika disimpan sebagai file, format, lokasi, permission, dan proses pembersihannya bergantung pada konfigurasi. Data session dapat mengandung identifier atau state sensitif, sehingga akses yang tidak semestinya berpotensi menimbulkan disclosure atau risiko integritas.

    Jangan menyimpulkan “log poisoning = RCE” atau “session poisoning = RCE”. Itu adalah label rantai kondisi yang memerlukan beberapa prasyarat sekaligus. Pengujian harus dilakukan secara terkendali pada sistem yang diizinkan, dan tidak perlu menulis data berbahaya ke log atau session produksi untuk membuktikan disclosure.
    10 / Linux Process Context

    /proc dan Informasi Runtime

    Pada Linux, /proc adalah pseudo-filesystem yang menyajikan informasi kernel dan proses. Beberapa entri di bawah direktori proses dapat memberikan konteks tentang environment, command line, working directory, file descriptor, atau memory mapping proses.

    ArtefakInformasi konseptualBatasan penting
    /proc/<pid>/environEnvironment yang terkait proses.Akses dipengaruhi permission, namespace, dan kebijakan sistem.
    /proc/<pid>/cmdlineArgumen command line proses.Dapat memuat argumen sensitif jika aplikasi menaruh secret di command line.
    /proc/<pid>/cwdReferensi ke current working directory proses.Resolusi dan akses tetap tunduk pada permission serta konteks proses.
    /proc/<pid>/fd/Referensi file descriptor yang terbuka.Setiap descriptor memiliki target dan permission yang berbeda.
    /proc/<pid>/mapsGambaran mapping memory proses.Bukan dump isi memori secara langsung; akses dapat dibatasi oleh kontrol kernel.

    Tree V5.0 menyebut beberapa path /proc/self/.... Kata self mengacu pada proses yang melakukan akses. Jika akses dilakukan melalui web server atau PHP-FPM, konteksnya adalah proses tersebut, bukan otomatis seluruh host atau proses lain.

    11 / Impact Boundary

    Kapan LFI Dapat Berkaitan dengan RCE?

    Remote Code Execution (RCE) berarti input yang dikendalikan dari jarak jauh menyebabkan kode atau perintah dijalankan pada sistem. LFI dapat menjadi salah satu komponen rantai menuju RCE pada konfigurasi tertentu, tetapi LFI sendiri tidak sama dengan RCE.

    Untuk menilai klaim RCE, setidaknya perlu dibedakan beberapa pertanyaan:

    1. File selection

    Apakah file yang dipilih benar-benar dapat dijangkau melalui titik inclusion?

    2. File content

    Apakah konten file dapat dipengaruhi pihak yang relevan, atau hanya dibaca sebagai data?

    3. Interpreter behavior

    Apakah runtime menginterpretasikan konten sebagai kode dalam konteks tersebut?

    4. Runtime configuration

    Apakah wrapper, ekstensi, dan pengaturan yang dibutuhkan tersedia?

    5. Process permissions

    Apa hak akses proses web dan batas filesystem yang berlaku?

    6. Evidence

    Apakah ada bukti aman dan terukur bahwa eksekusi benar-benar terjadi?

    Beberapa cabang yang tercantum pada Tree V5.0—seperti log poisoning, PHP wrapper, session poisoning, interaksi dengan /proc, dan file write—lebih tepat dipahami sebagai kelompok hipotesis rantai dampak. Masing-masing membutuhkan prasyarat berbeda dan tidak berlaku universal.

    Penulisan yang akurat adalah “LFI dapat berkontribusi pada rantai menuju RCE jika kondisi tertentu terpenuhi”, bukan “LFI menghasilkan RCE”. Jika yang terbukti hanya pembacaan file, laporkan sebagai file disclosure dan jangan menaikkan klaim dampaknya.
    12 / Observability

    Blind LFI dan Side-channel

    Blind LFI menggambarkan situasi ketika perilaku file inclusion tidak menampilkan isi file secara langsung. Peneliti mungkin hanya melihat sinyal tidak langsung yang berubah ketika aplikasi mencoba mengakses file atau memproses path tertentu.

    Jenis sinyalYang diamatiPotensi salah tafsir
    Time-basedPerbedaan waktu respons.Latency jaringan, beban server, cache, dan proses lain dapat memengaruhi waktu.
    Error-basedPerbedaan pesan atau kelas error.Error generik dapat menyembunyikan penyebab sebenarnya.
    Status-code basedPerubahan status HTTP.Middleware, autentikasi, routing, dan reverse proxy dapat mengubah status.
    Filter / response behaviorPerbedaan panjang, bentuk, atau karakteristik respons.Template, compression, dan dynamic content dapat menghasilkan noise.

    Hasil blind testing harus diperlakukan sebagai indikasi sampai dapat dikonfirmasi dengan bukti yang memadai. Catat baseline, ulangi pengamatan secara wajar, dan hindari pengujian berlebihan yang mengganggu layanan.

    13 / ZeroHitman Tree V5.0

    Percabangan LFI dalam Tree V5.0

    Bagian ini mempertahankan sembilan kelompok cabang dari Tree V5.0. Nama cabang dipertahankan agar pembaca dapat mencocokkan halaman ini dengan peta utama. Penjelasan di bawah menambahkan konteks dan batas teknis agar label cabang tidak disalahartikan sebagai hasil yang pasti.

    Ringkasan sembilan cabang

    1. File Read → Information Disclosure: kemungkinan informasi sistem, konfigurasi, credential, dan runtime.
    2. File Read → Source Code: pemahaman kode, konfigurasi framework, repository, dan dependency.
    3. RCE → Log Poisoning: cabang historis/bersyarat yang memerlukan file log dapat dipengaruhi dan diproses sebagai kode.
    4. RCE → PHP Wrapper: memeriksa dukungan wrapper dan kondisi interpreter; wrapper tidak otomatis memberi eksekusi.
    5. RCE → Session Poisoning: bergantung pada penyimpanan session, format, kontrol integritas, dan cara pemrosesan.
    6. RCE → /proc: mengacu pada interaksi dengan informasi proses; disclosure runtime bukan bukti RCE.
    7. File Write via LFI: istilah cabang untuk kondisi ketika rantai terkait memungkinkan perubahan file; LFI read-only tidak memberi kemampuan write.
    8. Blind LFI: inferensi melalui sinyal tidak langsung ketika konten tidak ditampilkan.
    9. LFI → Cross Technique: informasi dari file atau source code mengarahkan pemeriksaan teknik lain.

    LFI (include point ditemukan)

    Tree utama tetap menjadi peta hubungan. Ringkasan ini tidak menggantikan seluruh node asli; fungsinya memberi konteks agar pembaca memahami perbedaan antara file disclosure, source review, side-channel, dan rantai dampak bersyarat.

    15 / Reporting

    Bagaimana Menilai dan Melaporkan Temuan LFI?

    Laporan yang baik menjelaskan perilaku yang terbukti, konteks teknis, batasan, serta dampak yang masuk akal. Jangan hanya menuliskan “LFI → RCE” tanpa menjelaskan prasyarat dan bukti.

    Elemen laporan yang disarankan

    • Location: endpoint, parameter, fitur, dan role yang terpengaruh.
    • Root cause: bagaimana input memengaruhi pemilihan atau pemrosesan file.
    • Evidence: bukti minimal yang telah disamarkan dan dapat direproduksi sesuai scope.
    • File boundary: jenis file dan batas akses yang benar-benar teruji.
    • Execution context: aplikasi, runtime, OS, permission, dan konfigurasi yang relevan.
    • Impact: disclosure atau dampak lain yang telah dibuktikan, dipisahkan dari kemungkinan.
    • Limitations: file atau dampak yang tidak diuji, tidak dapat dijangkau, atau tidak terbukti.
    • Remediation: perubahan kode, permission, konfigurasi, dan kontrol tambahan.
    Saat menguji sistem client, gunakan file uji yang disetujui dan data non-sensitif. Hindari mengambil private key, password hash, credential aktif, atau data pengguna hanya untuk memperkuat bukti. Redaksi dan minimisasi bukti lebih baik daripada pengumpulan data berlebihan.
    16 / Defense

    Pencegahan dan Mitigasi

    1. Gunakan allowlist, bukan path bebas

    Terima identifier logis seperti home atau profile, lalu petakan identifier tersebut ke lokasi file yang telah ditentukan server. Hindari menjadikan input pengguna sebagai path langsung.

    2. Lakukan canonicalization dan validasi batas direktori

    Jika aplikasi memang harus menerima path, normalisasi path menggunakan mekanisme yang sesuai platform, resolusikan lokasi sebenarnya, lalu pastikan hasilnya tetap berada di direktori yang diizinkan. Perbandingan string sederhana dapat gagal menghadapi variasi separator, encoding, symbolic link, atau perbedaan filesystem.

    3. Pisahkan data dari kode

    Konten yang diunggah pengguna jangan ditempatkan di lokasi yang dapat di-include atau diinterpretasikan sebagai kode. Simpan upload di luar webroot atau pada storage khusus, dengan nama yang dibuat server.

    4. Terapkan least privilege

    Akun proses web hanya boleh membaca file yang diperlukan. Pisahkan secret dari direktori aplikasi yang dapat disajikan atau dimuat oleh fitur dinamis. Gunakan isolasi container dan filesystem policy sebagai lapisan tambahan, bukan pengganti validasi aplikasi.

    5. Batasi runtime features

    Nonaktifkan ekstensi dan wrapper yang tidak dibutuhkan. Atur PHP configuration dan pembatasan filesystem sesuai kebutuhan aplikasi. Jangan mengandalkan satu konfigurasi sebagai satu-satunya pertahanan.

    6. Lindungi secret dan artefak runtime

    Jangan menyimpan credential di source code atau log. Batasi akses log dan session, terapkan rotasi secret, serta hindari menampilkan path internal dan detail exception kepada pengguna.

    7. Logging dan monitoring

    Catat kegagalan file access dan pola input yang tidak wajar tanpa menyimpan secret mentah. Alert harus mempertimbangkan baseline aplikasi agar tidak menghasilkan terlalu banyak false positive.

    Prinsip pertahanan: batasi file yang boleh dipilih, batasi file yang dapat dibaca proses, dan pastikan konten data tidak berubah menjadi kode yang dieksekusi.
    17 / Final Understanding

    Kesimpulan

    LFI dimulai dari keputusan aplikasi untuk memuat file berdasarkan input atau state yang tidak dibatasi dengan benar. Temuan ini dapat membuka informasi sistem, konfigurasi, source code, atau artefak runtime. Dalam kondisi tertentu, informasi tersebut dapat menjadi petunjuk untuk investigasi teknik lain.

    Namun, file read tidak otomatis berarti file write; file write tidak otomatis berarti code execution; dan disclosure tidak otomatis berarti credential dapat digunakan. Setiap perpindahan dari satu cabang ke cabang lain membutuhkan kondisi dan bukti tersendiri.

    Pola pikir ZeroHitman

    1. Mulai dari perilaku yang benar-benar ditemukan.
    2. Kumpulkan informasi yang relevan dan catat sumbernya.
    3. Pilah fakta, indikasi, asumsi, dan hal yang belum diketahui.
    4. Gunakan informasi tersebut untuk menentukan cabang investigasi berikutnya.
    5. Validasi dampak sesuai scope dan gunakan bukti minimal.
    Satu temuan bukan akhir investigasi. Nilai sebuah temuan juga terletak pada informasi baru yang dapat membantu peneliti memahami aplikasi dan menemukan area yang perlu diperiksa berikutnya.
